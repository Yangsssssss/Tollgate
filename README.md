# Tollgate

> 大模型收费站 —— 统一的 API 闸口，按渠道分流，按 token 计量。

一个用 Java 21 + WebFlux 实现的大模型 API 网关：对外暴露 OpenAI 兼容协议，对内完成渠道调度、熔断降级与 token 计量。

它要回答的不是"能不能转发"，而是三个在响应式链路上特别难处理的问题：

**流式响应怎么边转发边计量、上游挂掉怎么在毫秒级切换、多实例下调度状态怎么保持一致。**

## 核心设计

| 关注点 | 做法 |
|---|---|
| 协议统一 | 对外 `/v1/chat/completions`，上游可为任意厂商，适配器负责转换 |
| 调度优先 | 候选集筛选 → 限流 → 加权选道 → 转发 → 故障转移 |
| 热路径零查库 | 渠道状态、密钥、限流计数全走内存 + Redis，DB 只在控制面和异步落账 |
| 计量可信 | 优先取上游返回的真实 usage，缺失时按字符估算并标记来源 |
| 可演进 | 控制面 / 数据面分离，Agent 调度与 MCP 以新模块接入 |

## 术语表

整套代码和文档统一使用这套词汇，避免同一个东西三种叫法：

| 术语 | 含义 |
|---|---|
| **Lane**（车道） | 一个上游渠道：厂商 + Base URL + 密钥池 + 权重 + 优先级 |
| **Toll**（过路费） | 一次调用的计量记录：token 数 + 成本 |
| **Tariff**（费率表） | 模型定价规则，按输入/输出 token 分别计价 |
| **Pass**（通行证） | 租户的预付费额度账户 |
| **Gate**（闸口） | 请求入口，负责鉴权与协议校验 |
| **LaneClosed** | 车道熔断关闭，暂停分配流量 |
| **ToolBooth** | V3 预留：MCP 工具调用的独立计量通道 |

## 一次请求的调度链

```
1. Gate        解析虚拟密钥 → 定位租户 → 额度与状态校验
2. Candidate   模型别名展开 → 剔除禁用/无密钥/熔断中的车道
3. RateLimit   租户 RPM/TPM 与车道并发预检，超限快速失败
4. Dispatch    优先级分层 → 层内平滑加权轮询 → 选出本次车道与密钥
5. Forward     构造上游请求 → SSE 流式透传 → 旁路嗅探 usage
6. Failover    超时/5xx/429 → 同层换道重试 → 驱动熔断器状态机
7. Toll        组装计量记录 → 入队 → 批量落库
```

熔断器状态机：`CLOSED →(失败率超阈)→ OPEN →(冷却)→ HALF_OPEN →(探测成功)→ CLOSED`

## 关键设计取舍

这一节是整个项目最值得看的部分——每个决策都有代价，写在明面上。

### 1. 热路径不查库

渠道配置、密钥池、限流计数全部驻留内存 + Redis，请求链路上零 SQL。

**代价**：配置变更要跨实例同步，存在一致性窗口。
**做法**：控制面写库后发 Redis pub/sub 广播，实例收到即刷新本地快照；另有 30s 兜底轮询防丢消息。
**收益**：P99 不受数据库抖动影响，DB 挂掉时存量请求仍可继续服务。

### 2. 手写熔断器，不用 Resilience4j

Resilience4j 的熔断器基于信号量/线程池，本质是**阻塞**模型。放进 WebFlux 的响应式链路会占住事件循环线程，在高并发下直接拖垮吞吐。

自己实现三态状态机：`CLOSED → OPEN → HALF_OPEN → CLOSED`，滑动窗口用 `LongAdder` 分桶计数，状态迁移用 CAS 保证并发安全。

**要处理的边界**：半开状态下必须严格只放行 N 个探测请求，否则刚恢复的车道会被瞬间打满——用 `AtomicInteger` 的 `tryAcquire` 语义实现。

### 3. SSE 透传不能简单 `bodyToFlux`

看起来一行 `resp.bodyToFlux(DataBuffer.class)` 就能转发，实际有四个坑：

- **要边转发边计量**：响应流被消费一次就没了，必须在透传同时旁路嗅探 `data:` 帧里的 `usage` 字段
- **DataBuffer 引用计数**：`retain()` / `release()` 配错就内存泄漏，且泄漏是静默的
- **客户端断连要取消上游**：否则上游继续生成、继续计费，白烧钱
- **首包超时 ≠ 总超时**：`first-token-timeout` 必须独立于 `request-timeout`，否则长文本生成会被误杀

### 4. 计量必须幂等

流式响应中途断开时，客户端已收到部分内容、上游可能已计费。此时重试换道，同一逻辑请求会产生多条计量记录。

**选择**：不做"精确一次"，做**至少一次 + 幂等去重**。以 `trace_id + attempt` 为幂等键，落账走 `INSERT ... ON CONFLICT DO NOTHING`。

理由：分布式下精确一次的成本远高于收益，而计费场景对"少记"的容忍度低于"重复记"——重复可由对账消化，漏记无法追溯。

### 5. 不追求纯响应式

控制面 API 和落账落库走 JDBC + Java 21 虚拟线程，不引入 R2DBC。

**代价**：技术栈不"纯"。
**收益**：MyBatis/JDBC 生态成熟、调试直观、团队上手成本低。数据库调用在虚拟线程上阻塞不会拖累事件循环——这是 Java 21 给的正解，不必为了纯度牺牲可维护性。

## 和现成方案的关系

New API（31K+ star）、LiteLLM（40K+ star）已经覆盖了网关类项目 90% 的功能，LiteLLM 与 One API 合计占国内企业自建网关 **82%** 的部署份额。

本项目不打算替代它们，也没有那个必要。它存在的目的是把网关里**最难讲清的几个问题**实现到可以逐行讨论的程度：

- SSE 流式透传下的背压、取消与旁路计量
- 响应式链路里的非阻塞熔断器
- 多实例下调度状态的一致性
- 计量的幂等与对账口径

选 Java/WebFlux 而非 Go/Python，是因为国内后端主力技术栈在这边，但缺少一个现代响应式实现可供参考。

## 数据模型

| 表 | 说明 |
|---|---|
| `tenant` | 租户，隔离维度 |
| `api_key` | 对外虚拟密钥，绑定租户 |
| `provider` | 上游厂商定义 |
| `lane` | 车道：厂商账号 + Base URL + 权重 + 优先级 + 状态 |
| `lane_key` | 车道下的上游密钥池 |
| `model` | 模型定义、别名、上下文长度 |
| `model_lane` | 模型 × 车道 可用映射，支持该组合下的权重覆盖 |
| `tariff` | 费率表：输入/输出单价（V2） |
| `request_log` | 调用明细：链路 ID、耗时、状态、车道、重试次数 |
| `toll_record` | 计量明细：prompt/completion token、成本 |
